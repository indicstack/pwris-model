Planner, worker, reviewer: how the plumbing works

A Claude session plans the work and reviews the result. An open model on the IndicStack API does the bulk reading. Plain scripts sit between every model step: they hold every fact and check every answer. Specs and settings are in the bundled PLANNER-WORKER-REVIEWER.md.

Figure 1 The Route

Model and script alternate. The model never passes its own output straight to the next model step — a script sits between every pair. Errors the review keeps finding become new script checks, which feed back into the plan.

StageStepWhoWhat happens
1aQueriesWorkerDrafts search queries from the brief. Every prompt quotes the brief rules word for word.
1bSearch & capScriptRuns queries, removes duplicates, applies the brief cap. Every ID comes from the source. Known facts go into the prompt as "harness facts".
2ScreenWorkerOne item per call. Answers: include, exclude, or uncertain. Uncertain goes on to full text. Without it, 13 known misses were exclusions over a fact the abstract didn't state.
3ExtractWorker ScriptExtract in groups of 8. A cut-off group is halved. Every quote is checked word for word against the source, one retry, then dropped. Failures go to a Claude queue.
4Normalise namesWorker ScriptSynonyms mapped to canonical names in batches. Script guards reject bad mappings. A failed batch stops the run instead of being skipped.
5ScoreScriptThe brief's rules, then the checks, then a deterministic ranking.
6Draft answerWorker ScriptWorker writes the final list and rationale from the script's ranking. Every departure is logged with its reason and record IDs.
7Review & gradeClaudeFresh session in an isolated folder corrects judgement. A separate grader script re-checks IDs, quotes, and rules.
Round 3 example: 1,302 IndicStack calls in 96 minutes. Extraction took 74–85% of wall time; screening 7–10%. That's where speed work belongs.

01 Who Does What

The open model reads, Claude judges, and scripts own the facts. In the Claude-only version of the example task, 74% of the cost was bulk reading by a Claude worker model. That is the part this pattern moves to IndicStack.

Planner Claude Code

Writes the brief and the harness, reads calibration and results, turns repeated review findings into script checks, prepares the review folder.

Does not: bulk reading.

+ details

Scripts Node harness

Search and fetch, caps, word-for-word quote checks, scoring rules, validation, every identifier, the call log.

Does not: judgement calls.

+ details

Worker IndicStack model

An open model (qwen38-27b in the example) with thinking off. Does search queries, screening, extraction, name normalising, and a draft of the final answer.

Does not: supply identifiers, or set the final order without the script's ranking.

+ details

Reviewer Fresh Claude session

A fresh Claude Code session in an isolated folder. Checks the workers' judgement on the outputs and corrects the final answer.

Does not: redo the work, or see project context.

+ details

Human Task owner

Rules the brief leaves open, the go-ahead for each run, final grading.

In the example, every judge so far has been a Claude model. A human grading is still pending.

+ details

The loop that makes it improve: When the reviewer catches the same kind of worker error twice, the planner writes a script check for it. In the example, the review replaced 6 of the top 10 in the first round and 1 on the 8 Oct output. The final list then matched the reviewer's corrected list.

Figure 2 One Worker Call, End to End

Every outcome has exactly one next step. The server has 16 parallel slots shared by all users, with LiteLLM queuing overflow fairly. The example capped itself at 8 screening and 6 extraction calls.

Prompt

Shared text first, task line last. Strict JSON schema. Thinking off. The server's prefix cache reuses the processed source text across calls on the same item.

Limiter

Waits for a free slot. One limit per stage. Screening starts at 6 (range 1–8), extraction at 4 (range 1–6).

Streaming client

Three clocks: first token, stall, total. Stops runaway repeats (last 400 chars repeated 4× in a row).

Outcome

One kind per call, logged as a JSONL line: stage, item ID, kind, seconds, time to first token, largest gap, prompt/completion/reasoning tokens.

Outcome → Action

OutcomeAction
okOn to the script checks.
lengthCut off at max_tokens. Split the group in half, then retry.
empty_contentBudget spent on hidden reasoning. Split or add a named fix, then retry.
bad_jsonNever resend unchanged. Add a named fix, then retry.
runawayLast 400 chars repeated 4×. Never resend unchanged. Add a named fix, then retry.
first_token_timeoutOne retry after 30 s.
stall / total_timeoutOne retry after 30 s.
502, 503, 504, network dropTry up to 3 times in all, waiting 2 s then 4 s. Nothing was produced, so a resend is safe.
429Honour Retry-After, otherwise wait 15 s then 30 s.
6 consecutive 429sCredit breaker: save state, exit with a distinct code, resume on the same command. Without it, a credit outage silently passes every remaining item.
Adaptive concurrency (AIMD): After twice the current limit in clean calls, the limit goes up by 1. On a 503 or 429 it halves. Calls already in flight finish; new ones wait until the count is under the limit.

Resume everywhere

Each stage appends to a JSONL file; on restart the latest line per item wins, and only failed items are redone.

Prefix cache

Calls on the same item share the system prompt and the source text; only the task line at the end changes. In the example, a paper's first read took 6.30 s to the first token (n=170) and a repeat 0.74 s (n=204). The trade-off: the source text is resent with every group call, so prompt tokens doubled (7.24M against 3.57M).

Calibration pilot

Before each long run, send about 50–60 calls on the hardest items you have, using the real prompts. Record: writing speed (p10 and p50), characters per token, time to first token (p95), largest gap between chunks (p99), answer length per call type (p95).

Write the settings to a calibration file stamped with the model name, and make the harness refuse a file from a different model; speed differed about 3× between two qwen versions. The planner reviews the file before use, and records each adjustment and its reason.

03 Script Checks Between Worker and Reviewer

Each check is deterministic code that never asks a model. Each was added after a run or a review exposed the error. Keep the worker's original output next to every correction, and count corrections in the run's metadata.

▸

Quote found word for word

Catches: invented or altered evidence. Result: 0 quote failures in every run.

▸

Quote names its subject

Catches: a real quote that doesn't mention the item it supports. Result: fell from 26% of records to 2%.

▸

Placeholder guard

Catches: the model writing "null", "none" or "n/a" as a value, which other steps then reuse. Result: one "null" had spread to 48% of records and ranked #1, though it passed schema checks. None reached the output after the guard.

▸

Variant numbers kept

Catches: different items merged because only a number differs (p-tau181, p-tau217 → "p-tau"). Result: 25 such merges in one run, all real errors.

▸

A failed batch stops the run

Catches: a skipped batch silently leaving data unprocessed. Result: one skipped batch had left 120 of 121 cohort names unmerged.

▸

Claim shown by its quote

Catches: a claimed rank or importance the quote doesn't show. Result: 262 claims downgraded; matched the reviewers on 27 of 29 records they judged.

▸

One source dominating

Catches: one paper's 12 dataset labels counted as 12 independent cohorts. Result: flagged and counted once, as a stated lower bound.

▸

Script ranking

Catches: a model acting on an advisory flag in one run and ignoring it in the next. Result: the model now starts from the script's order, and every move it makes is logged.

▸

Duplicate-name merge

Catches: one item under two names. Result: 15 groups merged; deliberately excludes cases that look alike but differ.

▸

Context documented

Catches: missing or wrong context (here, the specimen — brain tissue counted as a fluid). Result: source sentence found for 760 of 827 records; exactly the 2 cases the reviewers found were flagged.

▸

Independent grader

Catches: wrong IDs, quotes not found, ranking-rule violations. Result: a separate script, not sharing the harness's code.

04 The Isolated Review

The reviewer must judge the outputs, not the story around them, so it works with no project context. Each review in the example took 10–12 minutes with Opus 5.5.

1

Make a folder outside every project

e.g. C:\Users\<you>\eval-isolated\review-<date>\. Claude Code then loads no project CLAUDE.md, memory or history. Give it a neutral name, since the session sees its own path.

2

Copy in the frozen brief and the run's outputs

With model and harness names removed. Add the grader's report, relabelled the same way.

3

Leak scan

Search the folder for model, vendor and project names before starting.

4

Write one PROMPT.md — keep it byte-identical across reviews

So rounds can be compared. In the example it said:

▸ You are the lead reviewer: check the workers' judgement, don't redo their work.

▸ Work only with the files in this folder, and fetch a source only when a check can't be settled from the records.

▸ Checks, in order:

▸ are the sources behind each top item really independent?

▸ apply the ranking rules with your corrections, and log every departure with its reason and record IDs

▸ flag any rationale claim its records don't support

▸ spot-check 10 random records

▸ Never write an identifier or number from memory; use [VERIFY].

▸ Write one REVIEW.md (corrected table, corrections, flags, spot check, verdict), then stop.

5

Start a new Claude Code session in that folder

Send @PROMPT.md. Afterwards, check its transcript: it should have touched only its folder and the sources it fetched.

06 Setting Up a New Task

The planner session works through these in order. Steps 1–4 make no IndicStack calls. Every later step that does needs the task owner's go-ahead.

1

Write the brief

Cover the task, the inclusion rules, the fields to extract with their allowed values, the scoring and ranking rules, and the output files. List the judgement calls only the owner can make, and settle them now. Freeze it and record its hash.

2

Plan the folders

One dated folder per run, holding the call log, per-stage JSONL files, outputs and run metadata. Re-runs copy what they reuse and say so.

3

Build the scripts

Source fetch (every ID from the source), caps, the word-for-word quote check, scoring, validation, and an independent grader.

4

Build the client and limiter, test offline

Use a local stub server on 127.0.0.1 that simulates a hang, a stall, a slow reply, a runaway, a cut-off, an empty reply, broken JSON, a 503, repeated 429s and a resume. The example had 46 such tests.

5

Probe the model

One real call per model (a listing isn't proof of service); measure the served window with a max_tokens ladder; confirm thinking off works, the JSON schema is honoured, and 8 parallel calls succeed.

6

Write the worker prompts

Shared text first and the task line last; quote the brief's rules word for word; give known facts as harness facts; use a strict JSON schema; allow "uncertain" at screening.

7

Calibrate

On the hardest ~50 items. The planner reviews the settings file.

8

Smoke test

On about 25 items, then do the full run.

9

Grade, then run the isolated review

10

Turn repeated review findings into script checks

Re-run only the affected stages, into a new folder.

11

Have a human check a sample

Before anything is used. In the example, every judge so far has been a Claude model.

Planned for the example's next round (not built): a thinking-on second look, only at "uncertain" items and exclusions · a full-text pass for borderline exclusions, run alongside extraction · 16 items per extraction call, if cached prompt tokens aren't billed lower · more sources (trials, devices, preprints)

Setup on Windows

ON WINDOWS

Install Node.js 18 or later and Claude Code. No WSL, no Python, no npm packages. The harness uses only Node's built-in modules (fetch, streams, fs). Set the key once with:
setx INDICSTACK_API_KEY "<your key>"
Endpoint: https://api.indicstack.ai/v1 (OpenAI-compatible, vLLM behind LiteLLM).

Why Node rather than Python

On the machine where this was built, Windows 11 Smart App Control blocks native Python packages such as pandas at import, but the signed Node.js installer runs. If Smart App Control is off on your machine, either language works. Don't turn it off to make Python work.

Ground rules

▸

Facts come from scripts and sources. The model writes only judgement and prose. Never take an identifier, citation or number from model output; join it from the source.

▸

Keep the API key out of code, logs and git. Read it from an environment variable at runtime.

▸

Freeze the task brief before the first run. Hash it, and have the harness refuse to run if the hash changes. Rule changes go into a new brief version.

▸

Never overwrite a run. A re-run goes into a new dated folder that records what it copied.

▸

If the models stop responding, ask ops before reporting it. During this work, those periods were GPUs taken offline for optimisation, not faults.

07 Platform Notes for Ops

Things coders will trip over on the IndicStack API, each found by a probe or a run.

Thinking is on by default for qwen

A reply can come back blank once the budget is spent on hidden reasoning.

What coders should do: send chat_template_kwargs: {"enable_thinking": false} unless thinking is wanted.
Ask of ops: state the default in the docs.

+ details

Retired models stay listed in /v1/models

qwen3-8b, qwen36-27b, gemma4-31b all return 400 despite being listed.

What coders should do: send one test call per model; don't trust the listing.
Ask of ops: remove retired models from the listing.

+ details

/v1/models doesn't report the context window

The served window changed from 65,536 (30 Sep) to 131,072 (7 Oct) without notice.

What coders should do: measure it with a max_tokens ladder before relying on it.
Ask of ops: publish max_model_len, and give notice of changes.

+ details

Per-key credit cap returns 429

"your credit balance may be exhausted, or you are sending too fast"

What coders should do: treat repeated 429s as a pause, with a breaker and resume, not as a reason to resend.
Ask of ops: separate the credit message from the rate-limit message.

+ details

Writing speed per call varies by day

Extraction ran at 43 tokens/s per call on 30 Sep and 14.6 on 7 Oct.

What coders should do: calibrate before each long run; scale timeouts with the answer budget.

+ details

Prefix-cache reuse works

A paper's first read took 6.3 s to the first token; a repeat took 0.74 s.

What coders should do: keep the shared text at the start of the prompt and vary only the end.
Ask of ops: are cached prompt tokens billed at a lower rate? Are abandoned requests billed? [VERIFY]
